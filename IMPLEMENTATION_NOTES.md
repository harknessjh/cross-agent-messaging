# CAM/1 Implementation Notes

- Status: Non-normative compatibility and diagnostic notes
- Reference snapshot: 2026-08-25

These notes record one independently tested interoperability environment. They are not required for CAM/1 conformance, are not vendor commitments, and may become obsolete without notice. Use current product documentation and live capability discovery before relying on any interface described here.

The normative same-host profile is [PROTOCOL.md](PROTOCOL.md). The normative envelope schema is [cam-1.schema.json](cam-1.schema.json).

## 1. Reference environment and evidence limits

The observations below were made on macOS with both products running under one operating-system account:

| Component | Tested value | Evidence class |
|---|---|---|
| Codex CLI | `0.149.0`, retested with `0.149.1` | Local interoperability tests plus source pinned to commit `758ef40f50c1a458425c7cfbf1eb12cbc07af0b0` for the `0.149.0` baseline |
| Claude Code | `2.1.239`, retested with `2.1.243` | Local interoperability tests plus public product documentation |
| MCP protocol | `2025-06-18` | Successfully negotiated in the tested bridge |
| Codex platform | macOS, same operating-system account | Tested only in this configuration |

This draft does not yet include a public conformance suite; the observations here came from bounded manual interoperability tests. Native Windows, different user accounts, containers, cloud sessions, and remote-machine delivery were not tested for this snapshot.

## 2. Receiving Codex queue callbacks

In the tested Codex build, `codex queue` was a send-only CLI. Its help exposed target and message options but no supported `list`, `receive`, or `wait` operation. `codex agents` discovered sessions; it did not display their pending message bodies.

The normal behavior observed for an independent-session callback was:

1. The sender queued a CAM/1 envelope to the recipient's literal Codex thread UUID.
2. The recipient completed and yielded its active turn.
3. Codex delivered the queued item as a separate later user turn.
4. The recipient correlated the envelope and returned an application receipt.

A callback did not reliably interrupt a long, already-running turn. Native subagent waits observe only the current Codex collaboration tree; Claude peer state and `notify_when_idle` do not read a Codex queue. A sender should therefore finish its turn after sending and accept the callback on a later turn boundary.

Three events must remain distinct:

- the transport accepted the outbound item;
- the callback became pending in the destination product; and
- the recipient returned a correlated CAM/1 application receipt.

Only the third establishes receiver handling. `notify_when_idle` is a subscription notice, not a delivery receipt.

## 3. Experimental Codex App Server observer

For the pinned Codex build, the generated App Server interface exposed experimental `thread/queue/list` and `thread/queue/changed` operations. This is preferable to internal storage inspection when a controller already owns an authorized, persistent App Server connection.

The tested App Server stdio framing used one JSON object per line without a `jsonrpc` member. A minimal version-pinned sequence was:

```jsonl
{"method":"initialize","id":1,"params":{"clientInfo":{"name":"cam_controller","title":"CAM Controller","version":"1.1"},"capabilities":{"experimentalApi":true}}}
{"method":"initialized"}
{"method":"thread/queue/list","id":2,"params":{"threadId":"VERIFIED-THREAD-UUID","cursor":null,"limit":100}}
```

Send `initialize`, wait for response `id: 1`, then send `initialized`. Do not transmit the sequence as an unpaced burst. Use the schemas generated by the installed version and handle pagination through the returned cursor.

`thread/queue/list` is a point-in-time observation and does not consume an item. In the pinned source, `thread/queue/changed` is a subscription-scoped invalidation notice: it identifies a changed thread so the controller can list again. It is not the message itself, provides no replay guarantee, and should not be treated as an application acknowledgment. Do not load or resume a thread solely to establish this subscription because doing so can affect normal delivery.

This interface is experimental. Method names, payloads, retention, and notification behavior may change. `turn/steer` adds input to an active turn; it is not a queue-receive operation.

## 4. Internal storage diagnostic

Direct inspection of a product queue database is not a CAM/1 receive interface. It is an internal, version-specific diagnostic of last resort. Normal agents should not depend on it, and public automation should not parse it.

In the tested Codex build, a read-only inspection showed a `queued_items` table with stable-looking item IDs, a thread ID, queue order, timestamps, and a JSON payload. That observation explained why callbacks could be pending before they appeared as later user turns. It did not establish a stable storage contract.

If an authorized local maintainer must determine whether an exact thread has pending item metadata, the least invasive form is a metadata-only query:

```bash
sqlite3 -readonly -json "/absolute/path/to/queue_1.sqlite" <<'SQL'
PRAGMA query_only=ON;
SELECT id, queue_order, created_at_ms
FROM queued_items
WHERE thread_id = 'VERIFIED-THREAD-UUID'
ORDER BY queue_order;
SQL
```

This diagnostic is subject to all of these constraints:

- validate the database path and exact thread UUID before opening the file;
- use a read-only connection and `PRAGMA query_only=ON`;
- never insert, update, delete, acknowledge, reorder, vacuum, edit revisions, remove locks, or read the write-ahead log directly;
- do not copy or log raw payload bodies, which may contain sensitive transcript content;
- deduplicate observations by queue item ID rather than timestamp alone;
- treat a visible item only as evidence that it was pending at that instant; and
- treat absence as inconclusive because an item may not have arrived, may have started a turn, may have been explicitly deleted, may have been discarded as invalid, or may belong to another Codex home or thread.

Rows may remain visible after observation, and inspection can race normal delivery. If a maintainer has separately inspected authorized content, normal later-turn delivery may present it again; CAM/1 idempotency rules still apply.

## 5. Claude stdio MCP bridge fallback

The preferred bridge is a real child-process or MCP client with direct pipes. It keeps stdin writable, writes one UTF-8 JSON-RPC object per line, keeps stdout reserved for protocol messages, treats stderr as logs, and correlates every response by JSON-RPC ID.

One orchestration environment used during the reference test closed stdin for a long-lived non-TTY command. A pseudo-terminal kept stdin writable, but its default canonical line discipline truncated long one-line JSON-RPC requests and emitted terminal bell characters. Short sends could therefore succeed while longer sends produced no receipt.

For a dedicated POSIX pseudo-terminal only, this fail-closed fallback preserved long lines:

```bash
stty -icanon -echo min 1 time 0 || exit 1
exec "/absolute/path/to/claude" mcp serve
```

Run both lines inside the same dedicated pseudo-terminal. This workaround is not portable and can introduce carriage-return translation, stdout/stderr merging, terminal control characters, and framing ambiguity. Abandon it if the client cannot parse an initialization response and the expected response ID for every tool call. Never infer acceptance from the absence of an error.

Every new bridge process requires a fresh MCP `initialize` exchange, `notifications/initialized`, `tools/list`, and `ListAgents`. After a bridge restart, rediscover the target instead of assuming initialization state or addresses persisted. Keep messages bounded, but do not split one CAM envelope into independently actionable fragments unless a higher-level, hashed reassembly scheme is defined.

## 6. Anonymized interoperability incident

During the reference test, one Codex coordinator sent requests to two Claude Code sessions and remained inside a long active turn. Both Claude sessions returned callbacks. Codex subagent waits, Claude peer state, and a transcript search did not expose the pending items, so follow-up sends created duplicate callbacks. A bounded read-only diagnostic later showed the original and duplicate queue entries. Once the active Codex turn ended, callbacks appeared as separate user turns.

The resulting operational lessons were:

- peer state is not acknowledgment;
- transcript absence is not queue absence;
- a timeout inside an active turn does not prove recipient failure;
- every send needs both a transport receipt and an application receipt;
- retries reuse the semantic idempotency key; and
- receivers deduplicate before acting.

## 7. Exact-envelope and acknowledgment incident

A later first-contact test exposed two additional failure modes.

First, a receiver manually reconstructed a valid idempotency UUID, accidentally appended one hexadecimal character, and rejected the original message using the reconstructed value. The exact envelope preserved in the receiving turn still contained a valid `8-4-4-4-12` UUID and passed format-aware schema validation. A correlated correction retracted the rejection, and the independently queued valid request was processed exactly once.

Second, the Claude recipient returned an acknowledgment with matching sender claims, recipient session, request ID, receipt target, and nonce. Those correlations established application handling, but the acknowledgment omitted required CAM/1 fields and had no `body_sha256`. The response therefore could not close the CAM lifecycle as a conforming receipt.

The resulting operational lessons are:

- serialize once, validate the exact bytes that will be sent, and transmit that unchanged serialization;
- validate the exact delivered payload before extracting or reporting a field error;
- never retype, repair, normalize, or manually reconstruct a UUID for validation;
- preserve a false rejection as evidence, then issue a correlated correction without retrying the underlying action;
- generate replies from a complete envelope builder and validate them before queueing;
- classify a correlated but schema-incomplete reply as evidence of handling, not a conforming lifecycle receipt; and
- keep discovery evidence explicit: a live Claude name/ref is an address, while a human title, session UUID, working directory, and role mapping require separate operator-confirmed correlation when `ListAgents` does not expose them.

The reference [`tools/cam1.py`](tools/cam1.py) command was added after this incident to build complete first-contact and acknowledgment envelopes and to validate exact serialized payloads. Its regression tests preserve only synthetic identifiers and content.
